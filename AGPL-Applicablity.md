# AGPL and AI Model Use

The GNU Affero GPL (AGPL) is a **strong copyleft license** (like the GPL) that closes the “SaaS loophole” by requiring anyone who runs the software over a network to offer the source code of *any modified version*. In practice, this means:

* **Unmodified model use:** If you simply run an AGPL-licensed model *without changing its code or weights*, you are **not creating a “modified version”**, so AGPL’s source-distribution trigger does *not* automatically apply. In other words, using the model as-is (locally or as a service) does **not by itself force you to publish anything new**, beyond complying with the license terms (e.g. including a copy of the license).
* **Modified or distributed models:** If you **fine-tune, convert, or otherwise modify the model or its code**, or you distribute it to others, then AGPL applies. You must make your changes and “Corresponding Source” available under AGPL terms. Practically this means providing the model weights *and* any training/inference scripts or code needed to generate them. AGPL explicitly allows commercial use **and running the code unmodified** without restriction, but *any* public distribution (or network service) of a modified version requires releasing that source under AGPL.

In short, merely using an AGPL-covered AI model unaltered (even on an IoT device) does **not** trigger an obligation to open-source your application code. The network-sharing clause of AGPL applies **only to “modified versions”**. A company using the AGPL model on its own servers (with no code changes) would not have to publish any new source.

## Code Integration vs. Separation

Where AGPL’s copyleft **can spread** is in how you integrate the model with your software:

* **Linking or embedding:** If your application *directly includes or links to* the AGPL model code (for example, loading the model as a library or bundling it in your app), then your app is a derivative work. AGPL has *no linking exception*, so your code would **also need to be AGPL**. In other words, if your frontend/backend code uses the AGPL model “inline” or as a library, you must release that code under AGPL as well.

* **Separate process/API calls:** If instead the model runs as a separate service or process (e.g. you call it over a REST/IPC interface), many view that as a loosely coupled arrangement. In that case, your code and the AGPL software may be considered **independent works**. For example, Ultralytics (the creators of AGPL-licensed YOLOv8 models) clarify that the *service* hosting the model and its source must be open, but a separate web front-end or client need not be open-sourced. In general, running an AGPL model in a container or server and simply calling it from your own app can keep your code under a different license, as long as your code does not contain AGPL code. (However, this “clean separation” can be legally subtle; if your app depends so heavily on the service that they function as one program, some argue the copyleft could still apply.)

In practice, **the safe rule** is: any code or service that *directly uses* or interacts with the AGPL model should itself be AGPL. Ultralytics’ guidance is illustrative: if you deploy an AGPL model in a custom backend service, *that backend’s source must be available (including any model modifications)*. A pure front-end or mobile client that only calls the service, however, “may not need to be open-sourced” as long as it isn’t embedding the model. By contrast, a mobile app with the AGPL model embedded is treated as a derivative work, forcing you to provide the entire app (including model weights and code) under AGPL.

## Summary of Requirements

* **Using a pre-trained AGPL model *as-is*:** No obligation to release your own code changes, since you haven’t modified the AGPL work.
* **Modifying or fine-tuning the model:** You must open-source the modified model weights and related code under AGPL (i.e. provide “Corresponding Source”).
* **Embedding/linking the model in your code:** Your code becomes subject to AGPL, so you would need to release it under AGPL.
* **Calling the model via a separate API/service:** Likely treated as a separate work, so your calling code can remain closed (though the model service itself and its modifications must be AGPL).

## Example: RKNN Model Zoo Context

In your specific case, note that **the RKNN Model Zoo is actually licensed under Apache-2.0, not AGPL**. Apache 2.0 is permissive (no copyleft), so using those models carries no AGPL obligations at all. (The above AGPL rules would only matter if you obtained a model weight under an AGPL license – e.g. certain YOLO models trained by AGPL-licensed code.)



In summary, **using an unmodified AGPL model on your device does *not* force you to publish your app’s source**; only if you modify the model or incorporate it (or its code) into your own software will AGPL’s share-alike kick in. If the model is run as a standalone service, your frontend/backend code may remain under your chosen license, but the model and its immediate hosting code must remain open.
